# SLM 実験プロジェクト 概要・設計ポリシー

このドキュメントは、本リポジトリ（`/workspaces/slm`）におけるプロジェクト概要、アーキテクチャ設計原則、および実装ポリシーを定義します。

---

## 1. プロジェクト概要

chABSA データセットや livedoor ニュースコーパス等を使用し、**32トークンの文脈から次の単語（33単語目）を予測する小規模言語モデル（SLM）** を段階的に実験・検証するプロジェクトです。

### 実験世代と検証領域の構成
- **`impl_gen1`（第一世代：ベースライン）**
  - 語彙サイズ $V$ 次元の「重み付き ONE-HOT の総和」（予測単語からの距離 $d$ に応じた重み $1/d$ を加算）をそのまま特徴量 X（CSR 疎行列 `.npz`）とし、33単語目のトークンIDを正解ラベル Y（`.npy`）として学習・推論する世代。
- **`impl_gen2`（第二世代：3ハッシュ圧縮）**
  - 語彙インデックスの代わりに 3 つの独立した決定論的ハッシュ関数（ソルト付き SHA-256 先頭8バイト整数 `% vector_dim`）へ重み $1/d$ を加算し、特徴量 X を任意の次元数（デフォルト 256 次元）に圧縮して学習・推論する世代。
- **`impl_gen3`（第三世代：複数コーパス統合）**
  - 第一世代と同じ機械学習ロジックを用い、`phase1_preprocess` で chABSA と livedoor ニュースコーパスのフォーマット差を吸収し、共通 JSON フォーマット（`{"sentences": [{"original": "...", "lines": [...]}]}`）に統合してから学習・推論を行う世代。
- **`sandbox/`（要素技術・次世代アルゴリズムの検証）**
  - `sandbox/hdc/` 等において、Hyperdimensional Computing（HDC：超次元計算、バインド・バンドル・巡回シフトによる文脈表現など）の概念実証や単体テストスクリプトを実験する領域。

## 2. アーキテクチャ・設計ポリシー

### 2.1 世代間の独立性
- 各実験世代（`impl_gen1`, `impl_gen2`, `impl_gen3`, ...）は、それぞれ独立したディレクトリ構成（`src/libs/`, `src/pipelines/`, `src/batches/`）を持つ自己完結型とする。
- 新しい世代を作成する際は、既存の世代のコードが壊れないよう世代間で直接モジュールを共有せず、必要なライブラリやパイプラインを該当世代のディレクトリ配下に配置して改修する。

### 2.2 `libs` と `pipelines` の責務分離
- **`src/libs/`（コア機能ライブラリ）**
  - 正規化（`text_normalizer`）、トークナイザ探索（`sp_vocab_Remember` / `sp_tokenizer`）、特徴化（`weighted_onehot` 等）、NN学習（`nn_trainer`）、文章生成（`text_generator`）などの主機能を実装する。
  - **二刀流設計**: 他のモジュールから `import` して関数として呼び出せる（`__init__.py`）と同時に、`python -m <lib_name>` で単体 CLI コマンドとしても実行できる（`__main__.py`）ように作成する。
- **`src/pipelines/training/`（フェーズ実行・リソース管理）**
  - パイプラインの各フェーズを順番に実行する単位。主機能は `libs` を呼び出す形とし、パイプライン側は入出力パスの解決、メタデータ記録、コンテキストの引き継ぎを担当する。
  - 標準フェーズ構成：
    1. `phase1_preprocess`: 前処理（データ抽出・簡素化・正規化）
    2. `phase2_tokenize`: トークン化・SentencePiece 語彙サイズ探索
    3. `phase3_featurize`: 特徴量 X（`.npz`）および正解ラベル Y（`.npy`）の作成
    4. `phase4_training`: TensorFlow / Keras NN モデルの学習（エポック単位保存・中断再開 `--resume` 対応）
    5. `phase5_inference`: 学習済みモデルを用いた文章生成・目視確認用テキスト出力

### 2.3 `context.json` と `metadata.json` によるデータ引き継ぎ
- 各フェーズは前フェーズが出力した `context.json`（`--input-context-file`）を受け取り、必要な入力ファイル／ディレクトリパスを自動解決する。
- 各フェーズ完了時、既存の `context.json` の情報に自フェーズの出力パス情報を追記して次フェーズ用の `context.json`（`--out-context-file`）を書き出す。
- 実行時のパラメータ、入力・出力パス、統計情報や学習履歴は各フェーズの `metadata.json`（`--out-meta-file`）に JSON 形式で記録する。
- デバッグや単体実行がしやすいよう、`context.json` からの自動解決だけでなく CLI 引数による個別パスの明示的な上書き指定もサポートする。

### 2.4 トークン・文脈表現の規約
- 文脈ウィンドウ長（`context_length`）のデフォルトは `32`。
- 特殊トークンは原則として文頭パディング `<s>`（32個）、文区切り `<n>`、文書末尾 `</s>`（1個、末尾パディングなし）を使用する。

## 3. 開発環境・運用ポリシー

### 3.1 仮想環境とパッケージ管理
- Dev Containers（Python 3.11）環境を使用し、仮想環境は Docker named volume にマウントされた `/opt/venvs/.venv`（または `/opt/venvs/slm`）を使用する。
- 仮想環境の作成・有効化や `requirements-cpu.txt` / `requirements-gpu.txt` のインストールは自動実行せず手動で管理し、依存パッケージのバージョンは原則固定しない。

### 3.2 バッチスクリプトとデータ配置規約
- 一括実行スクリプト（`src/batches/run_all.sh` 等）は、**どのカレントディレクトリから実行しても動作する**ように実装する（`cd` でカレントディレクトリを変更せず、`BASH_SOURCE[0]` から絶対パスを解決する）。
- パイプラインの中間出力や学習済みモデル（`/tmp/job_gen*_1234` 等）、およびダウンロードしたコーパスデータ（`samples/`、`tmp/`、`_data/`）は Git 管理対象外（`.gitignore`）とし、リポジトリに大容量データを含めない。

### 3.3 コーディング・ドキュメント規約
- Python コードには型ヒント（`from __future__ import annotations`）と日本語の docstring / コメントを記載し、既存のコメントやドキュメントの整合性を維持する。
- 各世代の仕様変更や CLI オプションの追加を行った場合は、該当世代の `README.md` および `run_all.sh` の記述も同期して更新する。
