# SLM プロジェクト 技術ノート・問題解決履歴

このドキュメントは、SLM 実験プロジェクト（`/workspaces/slm`）における主要な技術的意思決定、パフォーマンス分析結果、およびトラブルシューティングの履歴を記録し、後続の AI エージェントや開発者が同じ試行錯誤を繰り返さないようにするための引き継ぎ資料です。

---

## 1. 特徴量表現と省メモリ設計（CSR 疎行列の採用）

### 1.1 背景と課題
- 本プロジェクトの第1世代（`impl_gen1`）および第3世代（`impl_gen3`）では、32トークンの文脈ウィンドウ内に現れる各トークン ID に対し、予測対象（33単語目）からの距離 $d \in \{1, \dots, 32\}$ に応じた減衰重み $1/d$ を加算した **語彙サイズ $V$ 次元の重み付き ONE-HOT 総和ベクトル** を入力特徴量 X とする。
- しかし、サンプル数が数百万件、語彙サイズ $V$ が数千〜1万数千次元になると、全学習データを `float32` 密行列としてメモリ上に保持することは不可能になる。
  - 例（`impl_gen3`）：`5,065,168` サンプル × `13,934` 次元 × `4 bytes` ＝ **約 282.3 GB**（RAM 枯渇で即座に OOM）。
- 一方、文脈長は 32 トークンであるため、1サンプル（1行）あたりの非ゼロ要素数は **最大でも 32 個（平均約 27 個、疎密度 99.8% 以上）** に限られる。

### 1.2 設計ポリシー
1. **ファイル保存形式**: Phase 3（`phase3_featurize` / `weighted_onehot`）では、特徴量 X を `scipy.sparse.csr_matrix` として構築し、`.npz`（圧縮 CSR 形式、506万件で約 415 MB、展開後の CSR 3配列 `indptr`, `indices`, `data` でも約 1.1 GB）として保存する。
2. **全件密行列化の厳禁**: 学習・推論のいかなる段階でも、データセット全体に対して `.toarray()` を呼び出してはならない。
3. **NN 入力層とのインターフェース**:
   - モデル構造（`Input(shape=(vocab_size,))` → `Dense(256, gelu)` × 2 → `Dense(vocab_size, softmax)`）を変更せず、Phase 5（`text_generator`）での 1 件ずつの密ベクトル推論と完全な互換性を保つため、**ミニバッチ（256件）単位でのみ密ベクトル `(batch_size, vocab_size)` に展開して NN に入力する**。

## 2. Phase 2（SentencePiece 語彙探索）のスコア特性と早期終了

### 2.1 背景と課題
- 形態素解析器（MeCab 等）＋人手による正規化（全角統一・英小文字化など）では、livedoor コーパス規模であれば数千語程度で主要語彙をカバーできる。
- 一方、本プロジェクトの Phase 2（`sp_vocab_Remember`）が使用する **SentencePiece（Unigram 言語モデル）** は、辞書を持たず文字の並びの統計的な出現頻度（対数尤度）のみでサブワード分割を決定する。
- `impl_gen3` のように「chABSA（有価証券報告書の会計・金融専門用語）」と「livedoor ニュース（IT・芸能・スポーツ・ネットスラング・記号）」を統合し、最小限の NFKC 正規化のみで学習させると以下の現象が起きる：
  1. 数字列・英単語派生形・複合名詞のパターンが膨大になり、`vocab_size=18,552` まで増やしても 1 トークンあたりの平均文字数（`chars/token`）が約 `2.01` 文字（目標 `2.5` 文字）にとどまる。
  2. Unigram モデルが高頻度な機能語（助詞・句読点・`<s>`・`<n>`）と低頻度な複合語に二極化しやすいため、評価式の正規化エントロピー項（`entropy ≈ 0.76`）が頭打ちになり、総合スコアが `0.73` 前後で飽和する。

### 2.2 設計ポリシー
- 語彙サイズ $V$ を無制限に増やすと、Phase 4 の NN の入力層（$V \times 256$）および出力層（$256 \times V$）のパラメータ数と計算量が比例して増大する。
- そのため、`phase2_tokenize` に `--score-threshold`（デフォルト `0.70`）を導入し、探索中に評価スコアがしきい値を超えた時点で探索を打ち切り、過大な語彙サイズになるのを防ぐ。

## 3. Phase 4（`nn_trainer`）GPU 学習のプロファイリングと高速化（2026-11）

### 3.1 対象環境・データセット条件
- **ハードウェア**: NVIDIA GeForce RTX 4060 (VRAM 5,560 MB)
- **データセット**: `impl_gen3`（`5,065,168` サンプル、語彙サイズ `13,934` 次元、非ゼロ要素総数 `nnz = 136,620,375`、各行の最大非ゼロ数 `max_row_nnz = 32`）
- **モデル・学習条件**: 入力 `13,934` → 隠れ層 `256 (gelu + LayerNorm + Dropout 0.1)` × 2 → 出力 `13,934 (softmax)`、Adam (`lr=0.001`)、`batch_size=256`（**`19,786` steps/epoch**）
- **改修前の問題**: GPU を使用しているにもかかわらず、1エポックあたり **216〜246 秒（約 11〜12.4 ms/step）** かかっていた。

### 3.3 実装した解決策（`impl_gen3/src/libs/nn_trainer`）

1. **C++ `tf.data` 上での固定長 2D Gather（`build_csr_tf_dataset`）**:
   - CSR の 3 配列（`indptr`, `indices`, `data`、合計約 1.1 GB）を CPU 上の 1 次元定数 Tensor として保持する。
   - 文脈長 32 の性質から 1 行の非ゼロ要素数は最大 `max_row_nnz = 32` 個であるため、RaggedTensor や可変長 SparseTensor（動的シェイプによるリトレースの原因）を使わず、2D インデックス Gather によって固定形状 `(batch_size, 32)` の列インデックス `col_padded` と重み `val_padded` を作成する（未使用スロットは `col=0, val=0.0` でマスク）。
   - これにより、CPU→GPU 間の PCIe 転送量が **14.27 MB/batch → 64 KB/batch（282.3 GB/epoch → 1.26 GB/epoch、99.5% 削減）** となり、`PyFunc` が完全に消滅した。
2. **GPU VRAM 上でのオンザフライ密展開と XLA コンパイル（`_attach_gpu_sparse_train_step`）**:
   - `model` 自身のレイヤー構造や保存形式は一切変更せず、`model.train_step` をラップする。
   - `@tf.function(jit_compile=True, reduce_retracing=True)` でコンパイルされた GPU 関数内で、`tf.tensor_scatter_nd_add` を用いて `(col_padded, val_padded)` から `(batch_size, vocab_size)` の `float32` 密テンソルを GPU 上で直接構築し、元の `train_step` に渡す（`.toarray()` との数値誤差は `max_diff = 0.0`）。
   - さらに `model.compile(steps_per_execution=64)` を設定し、Python と C++ ランタイム間のステップ毎の往復・進捗バー更新オーバーヘッドを削減した。
3. **後方・前方互換性の完全維持**:
   - 保存される `model.keras` は純粋な Functional Model のままであるため、**改修前に保存された `model.keras` に対して改修後のコードで `--resume` を実行してもそのまま高速に継続学習が可能**であり、Phase 5 の `load_model()` 推論とも 100% 互換である。
