以前の実験では、4800次元から256次元に圧縮すると、学習時間は800秒→600秒になったものの、正解率が49%で頭打ちになったという結果でしたね。

この結果を見ると、特徴量を削減するのではなく、4800次元を維持したまま疎な表現や低精度のデータ型でメモリを節約する方向は十分検討する価値があります。

特に、現在の「単語のONE-HOTを距離に応じた重みで加算する」方式なら、一般的な言語モデルよりもメモリ節約の余地があります。

## 1. まず考えられる方法

| 方法                 | 次元数    | 情報損失    | メモリ削減  |
| ------------------ | ------ | ------- | ------ |
| float32 → float16  | 維持     | 丸め誤差あり  | 50%    |
| float32 → bfloat16 | 維持     | 丸め誤差あり  | 50%    |
| float32 → int8量子化  | 維持     | 量子化誤差あり | 75%    |
| 疎行列（Sparse）        | 維持     | なし      | 非ゼロ数次第 |
| ビットマップ＋値配列         | 維持     | なし      | 非ゼロ数次第 |
| 重み行列の低ランク分解        | 入出力を維持 | 近似誤差あり  | 設定次第   |

ここで注意が必要なのは、入力データを圧縮しても、ニューラルネットワークの重み行列まで小さくなるとは限らないことです。

## 2. 最も相性が良さそうなのは疎行列

例えば4800次元の特徴ベクトルがあったとして、実際に値が存在するのが100次元だけなら、残り4700次元は保存する必要がありません。

通常の4800次元ベクトル（float32）

ゼロも含め4800個すべて保存：19,200 bytes

疎ベクトル（インデックス＋値）

124

641

1120

2040

3512

4401

100個の非ゼロ要素なら、int16のインデックス＋float32の値で約600 bytes

この例では、19,200 bytes → 600 bytes、約97%削減できます。

ただし、現在の特徴ベクトルが実際にどれだけ疎なのかが重要です。4800次元のほとんどに値が存在する場合、効果は小さくなります。

## 3. 入力ベクトルそのものを作らない方法

こちらの方が、現在のモデルには面白いかもしれません。

現在の特徴が次のようなものだとします。

\\[ X=\sum\_{i=1}^{N}w_i e\_{t_i} \\]

- \\(e\_{t_i}\\)：単語IDに対応するONE-HOT
- \\(w_i\\)：予測位置からの距離による重み
- \\(N\\)：文脈内の単語数

この特徴をニューラルネットワークの最初の全結合層に入れると、

\\[ Y=WX+b \\]

となります。

ここに先ほどの式を代入すると、

\\[ Y=\sum\_{i=1}^{N}w_i W e\_{t_i}+b \\]

となります。

つまり、4800次元の入力ベクトルを作らず、該当する単語IDに対応する重み行列の列だけを読み出して加算すれば、全く同じ計算になるわけです。

従来方式

単語ID＋重み

4800次元生成

全結合層

提案方式

単語ID＋重み

該当列だけ取得・加算

同一の出力

線形層の計算を変形しているだけなので、浮動小数点の加算順序による差を除けば数学的に等価です。

PyTorchなら `EmbeddingBag` の `per_sample_weights` が、この計算を実現する候補になります。

重要なのは、これは4800次元を256次元へ圧縮する方法とは異なり、特徴同士の衝突も情報の削除も起こさないという点です。

ただし、最初の重み行列自体は保持するため、モデルのパラメータ数は変わりません。

## 4. 学習時のメモリも減らしたい場合

例えば、入力4800次元、隠れ層512次元とすると、最初の重み行列は、

\\[ 4800\times512=2,457,600 \\]

個のパラメータを持ちます。

float32で約9.4MiBです。

Adamを使う場合は、さらに勾配と2種類の最適化用状態が必要になり、この部分だけでも概算で37.5MiBになります。

ここを減らすなら、

- SGDなど、保持する状態が少ない最適化手法に変更する。
- 重みやオプティマイザ状態を量子化する。
- 重み行列を分解する。
- バッチサイズを小さくする。

という対策があります。

ただし、CPU学習の場合、float16や量子化はメモリが減っても計算が速くなるとは限りません。むしろ遅くなる環境もあります。

## 5. 今回のモデルで試す順序

私なら次の順番で比較します。

1. gen1の4800次元をそのまま使い、入力だけ疎表現にする。
2. 最初の全結合層を `EmbeddingBag` 相当の演算に変更する。
3. float32を維持し、正解率と学習時間をgen1と比較する。
4. その後、float16・bfloat16・int8などを評価する。

特に2番目は、今までのモデルの学習結果を大きく変えずに高速化を試せる可能性があります。

ただし、一つ確認したいところがあります。

現在の4800次元は、単語ごとの独立した4800次元でしょうか。それとも、複数単語の特徴を圧縮・結合した結果の4800次元でしょうか？

前者なら `EmbeddingBag` 型への変更が有力です。後者なら、別のメモリ削減方法が適している可能性があります。
