はい。その方式はPyTorchなどで普通に実装できます。 むしろ、今回の言語モデルでは有力な省メモリ手法です。

考えている構造は、おそらく次のようなものですね。

学習データ全体

疎ベクトルで保存（インデックス＋値）

必要な1件（または1バッチ）を読み出す

非ゼロ要素だけ取得

密ベクトルに展開

4800次元のfloat32

NNで学習 → 次のデータへ

一時ベクトルを再利用・解放

これなら、全学習データを密行列で保持する必要がありません。

例えば100万件、4800次元のfloat32データなら、

- 全件密行列：約17.9GiB
- 1件の密ベクトル：約18.75KiB
- 256件の密バッチ：約4.69MiB

となります。

つまり、NNに投入する分だけ密ベクトル化すればよいので、学習データ全体に必要なメモリを大きく削減できます。

ただし、1件ずつ学習すると処理効率が悪くなりやすいため、通常はミニバッチ単位で展開する方が有利です。

## PyTorchでの実装例

一番簡単なのは、`Dataset`では疎データを保持し、`DataLoader`の`collate_fn`でバッチ単位の密ベクトルに変換する方法です。

```
import torchfrom torch.utils.data import Dataset, DataLoaderDIM = 4800class SparseDataset(Dataset):    def __init__(self, samples):        # samples: [(indices, values, label), ...]        self.samples = samples    def __len__(self):        return len(self.samples)    def __getitem__(self, index):        return self.samples[index]def collate_fn(batch):    x = torch.zeros(len(batch), DIM, dtype=torch.float32)    y = []    for i, (indices, values, label) in enumerate(batch):        idx = torch.as_tensor(indices, dtype=torch.long)        val = torch.as_tensor(values, dtype=torch.float32)        x[i].index_add_(0, idx, val)        y.append(label)    return x, torch.tensor(y, dtype=torch.long)loader = DataLoader(    SparseDataset(samples),    batch_size=256,    shuffle=True,    collate_fn=collate_fn,
```

この実装では、学習データ全体を密行列として作ることはありません。`index_add_` を使っているので、同じインデックスが複数あっても値を加算できます。

なお、`DataLoader`は疎テンソルを標準のバッチ結合処理で直接扱えないため、独自の`collate_fn`を使う方法が適しています。

## NN内部で直接処理することも可能

さらに進めるなら、密ベクトルへの展開自体を省略する方法もあります。

PyTorchの `nn.EmbeddingBag` は、インデックスと個別の重みを受け取り、必要な行だけを参照して重み付き合計を計算できます。

[image](https://www.google.com/s2/favicons?domain=https://docs.pytorch.org\&sz=32)

PyTorch 2.14 documentation+1



例えば、

\\[ X=[0,0,0.8,0,0.5,\ldots] \\]

を最初の全結合層に渡す代わりに、インデックス `[2,4]` と値 `[0.8,0.5]` だけで同等の線形演算を実行できます。

ただし、最初の層が通常の`Linear`である場合に適用しやすい方法で、モデル構造の変更が必要です。

## 今回の実験では

まずはバッチ単位で密ベクトル化する方法をおすすめします。

理由は、現在のgen1モデルのNN構造を変更しなくて済むからです。

比較するのは次の3種類で十分でしょう。

| 方式 | 学習データ保持 | NNへの入力     | モデル変更 |
| -- | ------- | ---------- | ----- |
| 現状 | 全件密行列   | 密ベクトル      | 不要    |
| 案A | 全件疎データ  | バッチごとに密変換  | 不要    |
| 案B | 全件疎データ  | 疎データから直接演算 | 必要    |

案Aで正解率が維持でき、メモリ削減を確認してから、案Bで速度改善を狙うのが合理的です。

なお、学習時の逆伝播に必要な中間データは残りますし、PyTorchのメモリアロケータが解放済み領域を再利用する場合もあります。そのため、OSから見たメモリ使用量が毎バッチ完全に減るとは限りません。

それでも、全件分のXデータを密行列で保持する必要がなくなることは大きな利点です。
